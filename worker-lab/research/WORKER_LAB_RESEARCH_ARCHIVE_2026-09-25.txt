==================================================
0. DEFINICIÓN CORRECTA DE WORKER
==================================================

La definición que debe gobernar este experimento:

Un worker NO es simplemente un modelo que responde una prompt.
Un worker es una shell/chat/agente inteligente, suficientemente capaz como ChatGPT, al que se le entrega un prompt fijo y que luego trabaja de forma autónoma durante una tarea larga, usando herramientas y completando un objetivo sin necesidad de intervención humana constante.

Problema de fricción a resolver primero:
HOY:
humano -> nuevo chat -> pegar prompt -> enviar -> worker trabaja

OBJETIVO:
sistema -> crear/lanzar worker -> inyectar prompt -> ejecutar autónomamente

El problema principal NO es todavía optimizar con modelos locales pequeños.
Los modelos locales/baratos quedan preservados como herramientas futuras para tareas simples.

4. CLOUD BROWSERS / COMPUTER USE REMOTO
==================================================

Se investigaron opciones para controlar un browser/computadora sin PC local:

Browserless:
- cloud browser
- Live URL interactiva
- human-in-loop
- puede persistir estado
- free tier recurrente limitado

Browserbase:
- cloud browser
- Live View
- Contexts para persistir cookies/storage/login
- permite login/MFA una vez y reutilizar contexto
- especialmente útil para auth persistente

Steel:
- browser remoto
- WebRTC/live viewer
- interactive control
- profiles persistentes
- créditos iniciales, no free recurrente permanente

Cloudflare Browser Run:
- Chromium remoto
- Playwright/Puppeteer/CDP/Stagehand
- free daily runtime limitado
- bueno para automación corta recurrente

Hyperbrowser:
- opción alternativa de cloud browser

Anchor Browser:
- opción para browser agents/authenticated sessions

Oracle Always Free:
- posible VM permanente gratuita
- podría alojar Chrome + Playwright + Browserless/noVNC
- más DevOps, más control

GitHub Actions:
- runners gratuitos en repos públicos
- útil para ejecución autónoma
- no es buen human-in-loop live desktop
- excelente para smoke tests y jobs automáticos

Arquitectura conceptual:
CELULAR
-> Worker Lab
-> crear CLOUD BROWSER
-> bot navega/clickea/escribe
-> si necesita identidad:
   mostrar LIVE VIEW
   humano login/2FA
-> bot continúa
-> sesión puede persistirse

==================================================

AI Horde 123B: 1/1

human_actions = 0
cost_usd = 0

Conclusión:
es posible crear una pista completamente autónoma y gratuita.

PERO:
esta pista NO sustituye a los workers principales deseados.
Los modelos locales/gratis de baja capacidad pueden servir después para:
- clasificación;
- routing;
- extracción;
- verificaciones simples;
- preprocesamiento;
- housekeeping;
- tareas mecánicas.

No deben confundirse con el worker principal estilo ChatGPT.

8. GATEWAYS / UNA CUENTA PARA MUCHOS PROVIDERS
==================================================

Hugging Face Inference Providers:
una cuenta/token puede actuar como gateway para distintos inference providers.
Potencial para reducir múltiples cuentas.
Free credits muy pequeños, útil más para smoke tests.

OpenRouter:
una cuenta/API key cubre muchos modelos.
Tiene modelos/rutas gratuitas.
Útil para reducir cuentas individuales.
Sigue existiendo una intervención inicial humana.

Pollinations:
la investigación inicial asumió acceso sin key, pero documentación actual cambió.
Ya NO se considera ruta zero-friction confiable para generación.

Puter.js:
puede dar acceso a muchos modelos sin API keys del desarrollador.
Modelo user-pays / usuario con cuota.
Puede requerir autenticación del usuario.
Por eso se considera casi-zero-friction, no zero-friction estricto.

9. CUENTAS, SSO Y SESIONES PERSISTENTES
==================================================

Idea investigada:
crear una única identidad LAB y reutilizarla con:
Google / GitHub SSO
+ cloud browser persistent context

Flujo:
login una vez
-> persistir cookies/storage
-> abrir provider
-> Continue with Google/GitHub
-> crear API key
-> mandar secret directo a Vault
-> tests automáticos
-> READY

La automatización puede eliminar:
- navegación;
- búsqueda de Settings/API;
- clicks;
- formularios no sensibles;
- copiar valores intermedios;
- health tests;
- model discovery;
- worker test.

Fricción humana que normalmente no puede eliminarse legítimamente:
- CAPTCHA;
- login inicial;
- 2FA/MFA;
- aceptar términos;
- confirmación sensible cuando el proveedor la exige.

Principio:
AUTO para todo lo automatizable.
HUMAN_REQUIRED sólo para identidad/consentimiento real.

11. DEFINICIÓN FINAL DEL PROBLEMA ACTUAL
==================================================

NO estamos buscando todavía:
- el mejor modelo local;
- el mejor router;
- el mejor benchmark;
- máxima cantidad de provider APIs.

Estamos buscando:
"¿Cómo lanzar automáticamente una shell/chat/agente suficientemente inteligente como ChatGPT, darle el prompt universal de worker y dejarla trabajar autónomamente, sin que el humano tenga que abrir y enviar 50 chats manualmente?"

ChatGPT UI:
técnicamente automatizable con browser automation, pero no se debe construir la arquitectura principal alrededor de UI automation si viola términos, es frágil o arriesga la cuenta.

ChatGPT Work:
parece conceptualmente cercano a un worker autónomo largo.
Debe investigarse cuidadosamente:
- límites;
- consumo;
- si puede lanzar chats normales;
- si puede actuar como launcher/orchestrator;
- si cada mensaje/acción consume su propia cuota;
- si puede durar 24 h;
- cómo preservar cuota Work;
- diferencia entre Work y chats normales.

Codex:
se investigó como opción oficial programable, pero el usuario NO quiere usar Codex para este experimento actual.

13. PRINCIPIOS QUE NO HAY QUE PERDER
==================================================

- Prometeo production NO se toca desde este laboratorio.
- Worker != model.
- Modelos locales pequeños son herramientas auxiliares futuras.
- El worker principal deseado es una shell/chat agentic de alta inteligencia.
- Human friction debe caer con el tiempo, no acumularse.
- Un sistema debe detenerse sólo ante una verdadera frontera humana.
- Nunca presentar DEMO/simulación como LIVE.
- Nunca decir READY si no hubo health + real test.
- Nunca filtrar secretos.
- Evidence/logs/screenshots deben demostrar el comportamiento real.
- Browser automation es infraestructura útil, no necesariamente el worker.
- La prioridad inmediata es eliminar el acto manual de "abrir chat + pegar prompt + enviar".
