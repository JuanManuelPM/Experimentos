==================================================
0. DEFINICIÓN CORRECTA DE WORKER
==================================================

La definición que debe gobernar este experimento:

Un worker NO es simplemente un modelo que responde una prompt.
Un worker es una shell/chat/agente inteligente, suficientemente capaz como ChatGPT, al que se le entrega un prompt fijo y que luego trabaja de forma autónoma durante una tarea larga, usando herramientas y completando un objetivo sin necesidad de intervención humana constante.

Problema de fricción a resolver primero:
HOY:
humano -> nuevo chat -> pegar prompt -> enviar -> worker trabaja

OBJETIVO:
sistema -> crear/lanzar worker -> inyectar prompt -> ejecutar autónomamente

El problema principal NO es todavía optimizar con modelos locales pequeños.
Los modelos locales/baratos quedan preservados como herramientas futuras para tareas simples.

4. CLOUD BROWSERS / COMPUTER USE REMOTO
==================================================

Se investigaron opciones para controlar un browser/computadora sin PC local:

Browserless:
- cloud browser
- Live URL interactiva
- human-in-loop
- puede persistir estado
- free tier recurrente limitado

Browserbase:
- cloud browser
- Live View
- Contexts para persistir cookies/storage/login
- permite login/MFA una vez y reutilizar contexto
- especialmente útil para auth persistente

Steel:
- browser remoto
- WebRTC/live viewer
- interactive control
- profiles persistentes
- créditos iniciales, no free recurrente permanente

Cloudflare Browser Run:
- Chromium remoto
- Playwright/Puppeteer/CDP/Stagehand
- free daily runtime limitado
- bueno para automación corta recurrente

Hyperbrowser:
- opción alternativa de cloud browser

Anchor Browser:
- opción para browser agents/authenticated sessions

Oracle Always Free:
- posible VM permanente gratuita
- podría alojar Chrome + Playwright + Browserless/noVNC
- más DevOps, más control

GitHub Actions:
- runners gratuitos en repos públicos
- útil para ejecución autónoma
- no es buen human-in-loop live desktop
- excelente para smoke tests y jobs automáticos

Arquitectura conceptual:
CELULAR
-> Worker Lab
-> crear CLOUD BROWSER
-> bot navega/clickea/escribe
-> si necesita identidad:
   mostrar LIVE VIEW
   humano login/2FA
-> bot continúa
-> sesión puede persistirse

8. GATEWAYS / UNA CUENTA PARA MUCHOS PROVIDERS
==================================================

Hugging Face Inference Providers:
una cuenta/token puede actuar como gateway para distintos inference providers.
Potencial para reducir múltiples cuentas.
Free credits muy pequeños, útil más para smoke tests.

OpenRouter:
una cuenta/API key cubre muchos modelos.
Tiene modelos/rutas gratuitas.
Útil para reducir cuentas individuales.
Sigue existiendo una intervención inicial humana.

Pollinations:
la investigación inicial asumió acceso sin key, pero documentación actual cambió.
Ya NO se considera ruta zero-friction confiable para generación.

Puter.js:
puede dar acceso a muchos modelos sin API keys del desarrollador.
Modelo user-pays / usuario con cuota.
Puede requerir autenticación del usuario.
Por eso se considera casi-zero-friction, no zero-friction estricto.

9. CUENTAS, SSO Y SESIONES PERSISTENTES
==================================================

Idea investigada:
crear una única identidad LAB y reutilizarla con:
Google / GitHub SSO
+ cloud browser persistent context

Flujo:
login una vez
-> persistir cookies/storage
-> abrir provider
-> Continue with Google/GitHub
-> crear API key
-> mandar secret directo a Vault
-> tests automáticos
-> READY

La automatización puede eliminar:
- navegación;
- búsqueda de Settings/API;
- clicks;
- formularios no sensibles;
- copiar valores intermedios;
- health tests;
- model discovery;
- worker test.

Fricción humana que normalmente no puede eliminarse legítimamente:
- CAPTCHA;
- login inicial;
- 2FA/MFA;
- aceptar términos;
- confirmación sensible cuando el proveedor la exige.

Principio:
AUTO para todo lo automatizable.
HUMAN_REQUIRED sólo para identidad/consentimiento real.

11. DEFINICIÓN FINAL DEL PROBLEMA ACTUAL
==================================================

NO estamos buscando todavía:
- el mejor modelo local;
- el mejor router;
- el mejor benchmark;
- máxima cantidad de provider APIs.

Estamos buscando:
"¿Cómo lanzar automáticamente una shell/chat/agente suficientemente inteligente como ChatGPT, darle el prompt universal de worker y dejarla trabajar autónomamente, sin que el humano tenga que abrir y enviar 50 chats manualmente?"

ChatGPT UI:
técnicamente automatizable con browser automation, pero no se debe construir la arquitectura principal alrededor de UI automation si viola términos, es frágil o arriesga la cuenta.

ChatGPT Work:
parece conceptualmente cercano a un worker autónomo largo.
Debe investigarse cuidadosamente:
- límites;
- consumo;
- si puede lanzar chats normales;
- si puede actuar como launcher/orchestrator;
- si cada mensaje/acción consume su propia cuota;
- si puede durar 24 h;
- cómo preservar cuota Work;
- diferencia entre Work y chats normales.

Codex:
se investigó como opción oficial programable, pero el usuario NO quiere usar Codex para este experimento actual.

13. PRINCIPIOS QUE NO HAY QUE PERDER
==================================================

- Prometeo production NO se toca desde este laboratorio.
- Worker != model.
- Modelos locales pequeños son herramientas auxiliares futuras.
- El worker principal deseado es una shell/chat agentic de alta inteligencia.
- Human friction debe caer con el tiempo, no acumularse.
- Un sistema debe detenerse sólo ante una verdadera frontera humana.
- Nunca presentar DEMO/simulación como LIVE.
- Nunca decir READY si no hubo health + real test.
- Nunca filtrar secretos.
- Evidence/logs/screenshots deben demostrar el comportamiento real.
- Browser automation es infraestructura útil, no necesariamente el worker.
- La prioridad inmediata es eliminar el acto manual de "abrir chat + pegar prompt + enviar".

14. INVESTIGACIÓN CHATGPT WORK · 2026-09-25
==================================================

Fuentes oficiales consultadas:
- https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex
- https://help.openai.com/en/articles/20001516-managing-usage-with-gpt-6-astra-in-work-and-codex
- https://help.openai.com/en/articles/20001478-reviewing-work-and-codex-usage-and-using-personal-analytics-in-chatgpt-desktop
- https://help.openai.com/en/articles/20001280-using-cloud-browser-in-chatgpt
- https://help.openai.com/en/articles/20001354-gpt-56-and-gpt-6-pro-in-chatgpt
- https://help.openai.com/en/articles/12642688-using-credits-for-flexible-usage-in-chatgpt-freegopluspro-sora
- https://help.openai.com/en/articles/10291617-scheduled-tasks-in-chatgpt

Hallazgos:

A. CHAT Y WORK SON EXPERIENCIAS SEPARADAS
Chat = conversación normal/rápida.
Work = agente para tareas largas y multi-step.
Codex = desarrollo/software.

OpenAI documenta que el uso de Chat es separado de la asignación agentic de Work/Codex.
Work y Codex COMPARTEN una misma asignación incluida.
Por lo tanto, quemar Work también reduce lo disponible para Codex y viceversa.
El uso regular de Chat no aparece en las vistas de consumo Work/Codex.

B. WORK NO ES "CHAT GRATIS EN BACKGROUND"
Work consume una asignación token-based/agentic.
El consumo depende de:
- modelo;
- input;
- cached input;
- output;
- razonamiento;
- Fast mode;
- cantidad de pasos;
- longitud de la tarea.

No hay un número fijo fiable de mensajes porque una tarea larga puede consumir mucho más que una corta.

C. VENTANAS DE USO
Según plan/cuenta pueden coexistir:
- ventana de 5 horas;
- límite semanal.

Para continuar cuando ambos aplican, debe quedar cuota en ambos.
La ventana de 5 horas se inicia con el primer uso de Work/Codex después de la ventana anterior.
Settings -> Usage muestra cuota y reset concretos de la cuenta.

D. ESTIMACIONES OFICIALES PARA PLUS POR 5 HORAS
No son límites fijos; dependen del trabajo.

GPT-6 Astra: aprox. 5-45 mensajes locales
GPT-5.6 Sol: aprox. 10-100
GPT-5.6 Terra: aprox. 25-200
GPT-5.6 Luna: aprox. 250-2000

Conclusión:
Luna puede rendir órdenes de magnitud más que Sol/Astra para coordinación simple.
Astra/Sol deben reservarse para trabajo que realmente necesita capacidad.

E. CÓMO ESTIRAR WORK
Las recomendaciones oficiales coinciden con:
- usar modelo más económico cuando alcance;
- reasoning bajo para tareas simples;
- evitar Fast mode si no hace falta;
- reducir input repetido;
- reducir outputs innecesariamente largos;
- evitar multi-step innecesario dentro de Work;
- aprovechar cached input;
- revisar Settings -> Usage.

Rates relativos publicados refuerzan la diferencia:
GPT-5.6 Luna es muchísimo más barato en tokens que Sol/Astra.
El output suele costar bastante más que cached input.

F. LUNA RESERVE
Algunas cuentas Plus/Pro tienen Luna Reserve.
Es una reserva separada que puede aparecer cuando se agota la cuota normal.
No está garantizada para todas las cuentas.
No es ilimitada.

G. WORK PUEDE CORRER EN BACKGROUND
Work en web/mobile puede seguir trabajando aunque el usuario cierre la conversación/computadora.
Puede usar Cloud Browser y pausar sólo cuando necesita:
- input humano;
- login;
- confirmación.

También soporta Scheduled Tasks para:
- una ejecución;
- recurrencia;
- trigger/monitoring.

H. SCHEDULED TASKS NO RESUELVE EL PROBLEMA DE SPAWN MASIVO
Las tareas programadas tienen límites de tareas activas por plan.
Actualmente:
Free/Go 3
Plus 5
Business/Edu 10
Pro/Enterprise 15

No hay documentación oficial que diga que una tarea Work pueda "crear 50 chats normales" y transferirles trabajo sin consumir la asignación de Work.
No debe asumirse.

I. HALLAZGO CLAVE PARA PROMETEO
No conviene ejecutar todos los workers dentro de Work.

Mejor arquitectura conceptual, si alguna vez usamos Work:

WORK (poco uso)
= ORQUESTADOR / HUMAN-BRIDGE / COMPUTER-USE
- inspecciona estado;
- abre browser si hace falta;
- realiza una acción de coordinación;
- deja evidencia;
- duerme/termina.

CHAT NORMAL (bolsa separada)
= WORKER PRINCIPAL DE ALTA INTELIGENCIA
si encontramos una forma oficial/permisible de iniciarlo automáticamente.

Esto preservaría Work para tareas que realmente requieren computer use o background agentic behavior.

J. PREGUNTA AÚN ABIERTA
No se encontró una interfaz oficial documentada donde ChatGPT Work pueda:
1. crear un nuevo Chat normal;
2. inyectarle un prompt;
3. hacer que ese Chat corra como worker independiente;
4. repetirlo programáticamente;
5. sin consumir Work por esos chats.

La UI podría técnicamente automatizarse con un browser, pero eso debe evaluarse contra términos de uso y fragilidad antes de considerarlo arquitectura.

K. CHAT NORMAL TIENE ALLOWANCES SEPARADAS
La documentación actual confirma:
- Chat tiene límites propios por modelo/plan.
- Work/Codex tienen asignación agentic aparte.
- En algunos esquemas Instant Chat es ilimitado o virtualmente ilimitado sujeto a guardrails; modelos fuertes tienen allowances propios.
- Por lo tanto, el objetivo de "usar Work sólo para lanzar Chat" tendría sentido económico si existiera un mecanismo oficial, pero hoy no está documentado.

L. OBJETIVO DE LA SIGUIENTE INVESTIGACIÓN
Buscar un mecanismo permitido y durable para:
"sistema -> lanzar Chat normal -> pegar prompt universal -> enviar -> dejarlo trabajar"
sin:
- usar Codex;
- convertir cada worker en Work;
- depender de modelos locales pequeños;
- hacer 50 acciones humanas.
